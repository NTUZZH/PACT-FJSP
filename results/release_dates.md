# Release dates: the candidate fourth timing rule, evaluated zero-shot

## Pre-run answers

1. **Purpose and destination.** Section 8.5 of the manuscript concedes that no fourth timing rule was implemented, while Section 3.4 argues that a release date meets the membership test with the trivial envelope. This run implements release dates and measures the released token-blind policy (jointblind-v1, three seeds) zero-shot against SPT, FIFO, MOR, MWKR and their per-instance best (rule pool) under the same release dates, on the 100 published 10x25 test instances of all eight regimes. The numbers land in `paper/tables/release_table.tex` and `paper/macros_release.tex` (\Rel... macros), to replace the concession in Section 8.5 with a measured result.
2. **Expected result and the reading of the alternative.** Expected: every schedule feasible (the release map is applied by the environment, not learned), zero bound violations (the potential keeps the trivial envelope, which stays admissible), and PACT still ahead of the rule pool on most regimes, with a smaller margin than without release dates because the observation carries no release channel and the policy never trained on staggered arrivals. If PACT falls behind the rule pool, the conclusion is that membership guarantees feasibility and an admissible reward but not zero-shot quality, so a new rule needs retraining (or a release channel); the paper would report that boundary. A validator failure or a bound violation would falsify the membership argument itself and would be reported as such.
3. **Contamination.** Evaluation only, CPU only (CUDA_VISIBLE_DEVICES empty, cores 0-7, OMP/MKL 4 threads, torch 1 thread). No checkpoint is written or resumed. All outputs are new files (the script refuses to overwrite `results/release_dates_raw.json`); no existing Result_*.npy is written. Wall-clock times are recorded but not reported as measurements (the box is shared). Test instances only; no training split is touched.
4. **Data accuracy.** Instances are the published `data/FAMILY/10x25/desc/<regime>/instance_000..099` descriptors on `data/PPVC/10x25+ppvc-mixed`, the same files the published evaluation read. Every arm is also run with release=None. The rule controls must reproduce the published `test_results/FAMILY/10x25/Result_*.npy` makespans exactly, instance by instance; the policy controls (published on the GPU, rerun here on the CPU) must stay within 1% of the published regime means. The script refuses to write any table otherwise.

## Release-date rule

rho_i ~ integer uniform on [0, floor(0.25 H)] hours per job, H = the descriptor horizon (job-chain lower bound incl. lags, identical in all regimes of an instance); numpy default_rng(20260926), instances in name order, one draw shared by the eight regimes. Mean H = 200.8 h. Mean release date 24.6 h (12.3% of H), max 53 h. Environment semantics: job-ready time initialised to rho_i on both time axes (start map b -> max(b, rho_i) on the first operation); potential unchanged (trivial envelope); no new observation channel; first decision at min_i rho_i with only jobs released then admissible (the non-delay rule restricted to readiness, as the published first decision is).
